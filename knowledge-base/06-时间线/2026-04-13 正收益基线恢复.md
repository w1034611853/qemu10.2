# 2026-04-13 正收益基线恢复

## 一句话结论

当前应把 `6d40860fef` 视为新的代码恢复基线。它对应
`performance_report/2026-04-09-nzcv-optimization-report.md` 记录的正收益/接近中性
性能状态；后续 broad RAW/main-state 路线虽然功能上能工作，但性能模型已经把所有
SPEC 对比拖成负收益。

## 为什么恢复

最新用户提供的性能对比显示优化版已经全面慢于 clean：

- `500.perlbench_r`: `0.722x`
- `502.gcc_r`: `0.771x`
- `505.mcf_r`: `0.775x`
- `531.deepsjeng_r`: `0.799x`
- `541.leela_r`: `0.843x`
- `557.xz_r`: `0.866x`

这不是单个 workload 的 miss path 问题，而是 broad RAW/main-state 逻辑把成本铺到了
大量 flag producer/consumer 上：原本赚钱的 same-TB gap direct path 被替换成
producer 写 `x86_raw_flags`、consumer 再读/解码 `x86_raw_flags` 的双重成本。

## 恢复分支形态

恢复分支：

- branch: `a64-x86-status4-positive-recovery-v10.2.0`
- worktree: `/home/wangruoyu/qemu10.2/.worktrees/positive-recovery-v10.2.0`
- code baseline: `6d40860fef`

恢复分支保留的内容：

- 2026-04-03 和 2026-04-09 性能报告
- Obsidian 知识库设计文档和 `knowledge-base/`
- CPUSPEC 功能/性能测试 runbook
- `scripts/cpuspec/` 下可给其他 agent 直接执行的测试脚本

恢复分支不保留的内容：

- `6d40860fef` 之后的 translator/backend/test 性能逻辑提交
- broad deferred-flags main-representation 消费者迁移
- compare-like producer sidecar shrink 作为默认路径的那组实现

## 后续优化原则

后续如果继续做 miss-case 改善，应按下面的顺序约束：

- 已知 future consumer 的 same-TB hit-case direct path 优先，不能被 RAW/main fallback 替代。
- RAW/main representation 只能作为真正 miss-case 或 unknown-consumer fallback。
- 不要默认把 RAW 状态跨 TB 放进 TB flags，除非有明确跨 TB 命中收益证据。
- 每一刀先跑 `502.gcc_r` 与 `505.mcf_r`：前者暴露全局成本，后者验证正收益路径是否还活着。

## 给后续 agent 的提醒

不要从最新 bad head 继续堆 consumer 或动态调节。正确的下一步是在恢复分支上重建，
先确认 2026-04-09 报告中的性能形态，然后只以小范围补丁恢复 miss-case 兜底。
