# 功能正确性总览

## 测试目标

确认当前 NZCV 优化线在较宽范围内没有破坏 guest 可见语义。

## 核心结论

截至 `2026-04-08`，当前证据支持“这条线在功能正确性上已经相当扎实”，但这并不意味着所有未来扩展都自动安全。现有结论是对 **当前已合入并已有验证的能力边界** 成立。

## 当前证据层次

### 1. 仓库内 focused checks

`progress.md` 记录了大量 focused host-direct checker 和二进制自检：

- `nzcv-status4`
- `cmpstress-o3`
- `adcsbc-bench`
- `check-adc-sbc-host-direct.sh`
- `check-cmp-*` / `check-logic-*` / `check-*-chain-host-direct.sh` 系列

它们证明：

- 当前 direct-path 确实命中了预期 path
- 许多细分 producer-consumer / chain 组合至少在 focused harness 下是对的

### 2. `531.deepsjeng_r test` 闭环

这条线非常重要，因为它曾经暴露 compare-like `CSEL/CS*` 的 correctness hole。

当前结论是：

- 直接 `531.deepsjeng_r test`
- 配合 `specdiff`

在主线文档中被记录为绿色。

### 3. 外部功能正确性报告

仓库外报告进一步覆盖：

- CoreMark
- Dhrystone
- 多项 SPEC CPU2017 `test` workload

其中 `525.x264_r` 还带有 `SSIM=1.000000000` 的输出级验证。

## 证据强度应如何理解

- 对已写入 focused harness 的路径，信心较高
- 对已经通过外部 benchmark test-size 的工作负载，信心进一步提高
- 对最近刚扩出的更深 chaining 组合，虽然已有 focused evidence，但是否已经足够代表更宽 workload，仍要保守解读

## 当前边界

- `500.perlbench_r test` 不能直接当作“优化正确性失败”的干净信号
- focused checker 通过不等于未来任何扩展都不会破坏 lifecycle
- 某些 external report 的测试对象版本停在 `2026-04-03` 左右，需要与 `as_of` 区分

## 人类应如何使用这份结论

如果你的问题是“现在这条线是否还处于明显不可信状态”，答案是否定的。
如果你的问题是“这意味着可以随便继续放宽生命周期边界吗”，答案仍然是否定的。
