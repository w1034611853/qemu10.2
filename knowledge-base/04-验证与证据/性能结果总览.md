# 性能结果总览

## 一句话结论

当前性能故事分成两个阶段：`6d40860fef` 附近证明过部分 workload 可以正收益；
但后续 broad RAW/main-state 路线在最新对比中已经全面负收益。因此当前代码恢复基线
应回到 `6d40860fef`，再重新小步加入 miss-case fallback。

## 2026-04-09 正收益基线

| Benchmark | 结论 |
|---|---|
| `505.mcf_r` | 明显收益，约 `+12.8%` |
| `502.gcc_r` | 基本持平 |
| `531.deepsjeng_r` | 明显回退，约 `-11.0%` |
| `541.leela_r` | 明显回退，约 `-7.2%` |
| `500.perlbench_r` / `557.xz_r` | 运行时间过短，噪声较大 |

## 2026-04-13 最新负收益信号

用户提供的最新对比显示，后续 broad RAW/main-state head 已经全面慢于 clean：

| Benchmark | Speedup |
|---|---|
| `500.perlbench_r` | `0.722x` |
| `502.gcc_r` | `0.771x` |
| `505.mcf_r` | `0.775x` |
| `531.deepsjeng_r` | `0.799x` |
| `541.leela_r` | `0.843x` |
| `557.xz_r` | `0.866x` |

## 当前应该如何解读

- 这条优化已经证明“不是纯理论收益”，因为 `505.mcf_r` 在 `6d40860fef` 基线下有提升
- 它也证明“不能默认 everywhere-on”，因为 broad RAW/main-state 让全套结果转负
- 后续应优先保护 same-TB hit-case direct path，把 RAW/main fallback 限定为真正 miss-case 兜底

## 这份证据的边界

- 当前主性能报告的被测优化版本主要停在 `6d40860fef` 一轮
- 之后的 chaining 扩展不应被自动套用为“也具有同样 perf 结论”
- 这份证据更适合作为“路线选择参考”，而不是“最新 head 的精确 perf 声明”
