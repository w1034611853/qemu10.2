# 当前状态总览

## 一句话结论

截至 `2026-04-13`，当前推荐继续演进的代码起点已经恢复到 `6d40860fef`：
这是 2026-04-09 性能报告记录的正收益/接近中性基线。后续 broad
RAW/main-state 路线作为历史方案保留在文档和知识库中，但不再作为当前代码基线。

## 当前恢复分支

- branch: `a64-x86-status4-positive-recovery-v10.2.0`
- worktree: `/home/wangruoyu/qemu10.2/.worktrees/positive-recovery-v10.2.0`
- code baseline: `6d40860fef`
- 保留内容：性能报告、Obsidian 知识库、CPUSPEC runbook 和脚本
- 排除内容：`6d40860fef` 之后的 translator/backend/test 性能逻辑提交

## 当前可以认为“已站稳”的部分

- `ADCS/SBCS` direct-consumer 线已经完成并保持绿色
- `lazy compare phase 2` 的 `B.cond` 第一轮 rollout 已经形成可工作的 bounded-gap 模型
- compare-like non-branch support 已恢复，其中 `CSEL/CS*` 采用了 correctness-first 的 rework 模型
- focused TCG checks、`nzcv-status4`、`cmpstress-o3`、`adcsbc-bench` 和 `531.deepsjeng_r test`
  都已被记录为通过
- 外部功能正确性报告覆盖到 CoreMark、Dhrystone 和多项 SPEC CPU2017 `test` workload

## 需要显式看到的恢复边界

`366b7d6ddb`、`0c9d65605b` 以及后续 deferred-flags main-representation /
sidecar-shrink 系列不在当前恢复代码基线内。它们仍然是重要历史材料，但最新
性能结果显示这条 broad RAW/main-state 路线把原本部分正收益的状态推成了全面负收益。

恢复分支的目标不是否定所有后续想法，而是重新确立约束：

- direct hit-case 先赚钱
- miss-case fallback 只兜底
- 不让 RAW/main-state 变成 everywhere-on 的默认成本

## 当前最重要的结构性认识

### 1. correctness 依然是第一约束

最典型的证据就是 compare-like `CSEL/CS*` 的路径：先前的 `peek + keep alive`
模型不是“局部有 bug”，而是生命周期边界本身不够稳。当前路线已经明确偏向：

- direct 条件消费可以保留
- 但 consumer 之后的 flags 可见性必须尽快回到稳定表示

### 2. current state 是“保守扩展”，不是“全面 lazy flags”

虽然 direct-path 和 chaining 范围在扩大，但设计仍然明显保守：

- bounded gap
- whitelist
- invalidation-first
- 一次只扩大一个 consumer family 或一类 chaining 形态

### 3. performance 不能简单按“路径覆盖率”判断

外部报告显示：

- `505.mcf_r` 有明显收益
- `502.gcc_r` 基本持平
- `531.deepsjeng_r`、`541.leela_r` 存在回退

所以当前状态应该解读为：

- correctness closure 已经相当扎实
- performance story 仍然是 workload-dependent

## 当前建议如何理解“做到哪了”

如果是为了后续继续开发，可以把当前状态粗分为三层：

### 稳定层

- 已有 focused tests 和更宽 workload 结果支撑的主线能力

### 观察层

- 最近两笔 chaining 扩展已经进入主分支，但还需要更多知识化整理和统一叙事

### 规划层

- 下一步更像是在做 selective expansion、performance refinement 和路线选择
- 而不是从零搭基本机制
